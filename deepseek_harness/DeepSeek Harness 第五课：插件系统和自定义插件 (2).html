DSH 插件系统与自定义插件开发：先理解架构，再决定怎么写

本节重点：先弄清 DSH 插件系统中的术语和运行关系，再理解一个 DSH 实例是怎样组装出来的，最后才讨论自定义插件应该从哪里入手。

本文以 DSH 官方仓库文档为依据。不同版本的扩展接口可能调整，动手前应以当前安装版本的官方文档和配置输出为准。

一、先理解几个核心术语

1. DSH

DSH（DeepSeek Harness）是运行 AI Agent 的应用框架。它不只是一个聊天界面，还包含模型调用、工具执行、会话记录、权限与沙箱、Agent 执行循环等能力。

理解时可以把 DSH 看成一个“可组装的应用运行环境”：启动时根据配置，把需要的能力组合起来。

2. Plugin（插件）

插件是实现某项能力、并能接入 DSH 运行环境的代码模块。

例如：

  • 模型适配插件：负责把 DSH 的模型请求转接到某个模型服务。
  • 工具插件：向 Agent 提供可调用的工具。
  • 会话插件：负责会话记录或持久化。
  • 自定义业务插件：监听 Agent 事件、增加命令，或接入外部服务。

DSH 的设计理念是：模型适配器、工具注册表、会话日志乃至 Agent Loop 本身也可以由插件形式提供。因此，插件不只是给现有软件“加一个小功能”，也可以参与构成运行环境本身。

3. Cordis

Cordis 是 DSH 底层使用的插件框架。它负责组织插件、管理插件之间的依赖，并让插件通过共享上下文协作。

可以这样区分：

  • DSH：完整的 Agent 应用及其运行环境。
  • Cordis：负责组织、连接和管理插件的底层框架。
  • Plugin：通过 Cordis 接入运行环境的能力模块。

Cordis 的几个常见概念：

术语 含义 可以怎样理解
ctx / Context（上下文） 插件运行时共享的上下文，可提供服务、事件和运行环境信息 插件之间约定好的“公共工作台”
Service（服务） 插件通过上下文提供、供其他插件使用的能力 一个插件对外提供的接口
Dependency（依赖） 插件运行前需要的其他服务或插件 “我需要先有某项能力，才能工作”
Event（事件） 运行过程中发出的通知或扩展点，其他插件可以监听 在某个流程节点接入自己的逻辑
Effect（副作用） 插件注册服务、监听事件、创建定时器等对运行环境产生的改变 插件启用时做的事情，需要在卸载时妥善清理
inject 声明插件需要哪些上下文服务，供框架进行依赖处理 明确告诉框架“我依赖什么”

注意：ctx 不是任意全局变量，也不是所有功能都能直接从中调用。具体有哪些服务，取决于当前 Profile 实际加载了哪些插件。

4. Profile（运行配置组合）

Profile 是一套可启动的运行环境配置，决定这个 DSH 实例要组合哪些 Bundle、安装哪些外部插件，以及应用哪些自定义配置。

常见 Profile 包括：

  • web：Web 交互界面。
  • headless：无 Web 服务的一次性运行模式。
  • sdk：提供 SDK 使用的运行入口。
  • acp：面向自动化协议场景的运行入口。

例如，dsh --profile headless 表示启动 headless 这套组合，而不是“加载一个名为 headless 的插件”。

5. Bundle（插件组合包）

Bundle 是分发和组合插件配置的一种包格式。它通常是一个 npm 包，里面可以包含：

  • 插件代码；
  • cordis.patch.yml 配置层；
  • package.json 中的 DSH Bundle 声明。

Bundle 的作用是把一个或多个插件及其配置整理成可安装、可复用的分发单元。

关键区别：

  • Plugin 关注“提供什么能力”。
  • Bundle 关注“如何把插件及配置打包、分发和接入”。
  • Profile 关注“本次运行由哪些 Bundle 和配置组成”。

Plugin、Bundle、Profile 不是同一个东西。 一个插件可以通过本地配置直接加载；如果要方便安装和分发，再把它组织成 Bundle。

6. Patch / cordis.patch.yml

Patch 是对插件配置树进行插入或覆盖的配置层。DSH 启动时，会按顺序叠加配置层。

Patch 常见用途：

  • 插入一个新的插件配置项；
  • 修改已有插件的配置；
  • 替换某个配置项所使用的插件实现。

例如，下面的配置表示插入一个插件条目：

- insert:
    - id: hello
      name: ./hello-plugin.js

这里的 id 是配置树中用于定位该条目的标识，name 指向要加载的插件模块。相对路径的解析规则与 Patch 文件的位置有关，实际使用时应按照官方文档及当前版本的配置格式操作。

需要特别注意：Patch 覆盖某个条目时，可能替换该条目的整个 config，并不一定会自动合并原来的所有字段。 修改现有条目时，要确认需要保留哪些配置。

7. dsh plugin 命令

这是用于管理插件包的 CLI 命令，例如把一个 Bundle 安装到指定 Profile，或从 Profile 中移除它。它是“管理插件安装”的命令，不等于插件代码本身，也不等于 Cordis 的运行机制。

二、DSH 的插件架构是怎样工作的？

1. 先看整体关系

用户启动命令
    │
    ▼
DSH Launcher（启动器）
    │  选择 Profile，例如 web / headless
    ▼
Profile（本次运行的组合方案）
    │
    ├── Bundle A：基础能力
    ├── Bundle B：运行界面或运行模式能力
    ├── Bundle C：用户安装的扩展包
    │
    ▼
Patch 配置层按顺序叠加
    │
    ├── Bundle 自带的 Patch
    ├── Profile 自己的 cordis.patch.yml
    ├── 用户级 Patch
    └── 命令行 --patch 指定的覆盖层
    │
    ▼
Cordis 根据最终配置加载插件
    │
    ├── 插件通过 ctx 提供服务
    ├── 插件声明依赖并使用其他服务
    └── 插件监听事件、注册工具或扩展行为
    │
    ▼
组成可运行的 DSH Agent 环境

这张图要表达的核心是：Profile 决定组合方案，Bundle 负责分发插件和配置，Patch 决定配置如何叠加，Cordis 负责在运行时组织插件。

2. 启动时，配置是怎样组合的？

在常见的基于 Bundle 的 Profile 中，配置通常按以下顺序叠加：

  1. Profile 声明的 Bundle，按列表顺序应用；
  2. Profile 自己的 cordis.patch.yml；
  3. 用户级的 cordis.patch.yml；
  4. 命令行通过 --patch 传入的覆盖层。

后面的配置层可以覆盖前面层中同一个 id 对应的配置项。

例如，基础 Bundle 提供了一个模型适配器，用户可以在自己的 Patch 中针对相应条目进行替换或调整，而不必直接修改 DSH 源码。

不过，Patch 是按配置规则叠加，不代表所有字段都会深度合并。覆盖条目时应重新检查完整配置，避免无意间丢失原有设置。

3. 插件之间怎样协作？

插件并不是互相随意调用文件，而是通过 Cordis 提供的服务和事件协作。

方式 A：通过服务协作

例如，插件 A 提供某项能力，插件 B 声明自己依赖该能力，之后通过上下文访问服务。这样依赖关系是明确的，不需要把所有逻辑写进一个巨大的插件。

方式 B：通过事件扩展流程

例如，Agent 在执行某个步骤、发起模型请求或调用工具时，会经过相应的事件扩展点。插件可以监听这些事件，在合适的时机增加校验、记录日志或调整行为。

事件并不都具有相同语义：有些是通知，有些是允许监听器参与决策的流程节点。编写监听逻辑前，必须确认该事件的参数、调用顺序，以及是否需要调用 next() 等约定，不能把所有事件都当作普通回调。

4. 自定义插件通常从哪里接入？

不要一开始就尝试修改 Agent Loop 或 DSH 源码。先确定你要改变的行为，再选择对应的扩展点。

想实现的功能 优先调查的方向
给 Agent 增加一个可调用的工具 ctx.tools 及工具注册相关文档
增加用户输入命令 ctx.commands
在 Agent 执行过程中观察、校验或干预 对应的 agent/* 事件
在工具执行前后增加策略或日志 tools/* 事件
修改或扩展模型服务 ctx.llm 及模型适配器接口
为模型请求提供额外上下文 Agent 的上下文注入能力及相关事件
增加文件系统能力或访问策略 ctx.fs 或 fs/* 事件
接入外部 Webhook ctx.webhookRuntime 及对应适配器

表格是选型入口，不是可以直接照抄的 API 清单。具体接口名称、类型和参数应以你所用版本的官方扩展文档为准。

三、准备自定义插件之前，先回答三个问题

问题 1：我要解决什么问题？

先用一句话描述目标，例如：

  • “我希望 Agent 能查询内部 API。”
  • “我希望每次工具执行前都记录审计日志。”
  • “我希望给 Agent 增加一个获取当前项目摘要的工具。”

目标要具体到可以验证，而不是笼统地说“我要开发一个插件”。

问题 2：这个功能应该放在哪个扩展点？

根据目标判断它属于哪类扩展：

  • 新增能力：通常考虑注册工具或服务；
  • 观察已有流程：通常考虑监听事件；
  • 改变现有实现：先检查能否通过 Patch 替换对应插件或配置；
  • 新增一套运行模式：这可能涉及 Profile / Bundle 组合，而不只是单个插件。

优先使用 DSH 已经提供的扩展点。只有在现有接口无法满足需求时，再考虑更深层的框架改动。

问题 3：我是要本地试验，还是要安装分发？

这是选择开发路线的关键。

路线 A：本地开发和验证

适合学习、实验和团队内部使用。先写插件模块，再通过一个本地 Patch 将它加载进现有 Profile。这样可以先验证插件逻辑，不必一开始就处理包发布、版本和依赖管理。

路线 B：打包成可安装 Bundle

适合需要在不同机器、不同 Profile 或团队成员之间复用的插件。此时再补充 package.json 中的 dsh.bundle 声明、Bundle 的 Patch 文件和必要的依赖信息，并通过 dsh plugin 安装到目标 Profile。

建议顺序：先验证插件逻辑，再整理 Bundle；不要把“写插件”和“发布插件包”混成第一步。

四、自定义插件的最小开发思路

本节先给开发路线，不急于把所有 Cordis API 一次性塞进示例中。

第一步：确定入口模块

一个基础的 Cordis 插件模块通常会导出插件名称和 apply 入口。下面是官方打包示例所采用的最小形式：

export const name = 'hello-plugin'

export function apply() {
  console.log('[hello-plugin] plugin loaded!')
}

它的作用只是验证“模块是否成功加载”。此时还没有注册工具、监听事件或使用其他服务。

第二步：通过 Patch 加载它

在本地 Patch 中插入插件条目，让 DSH 在启动时加载这个模块。路径、模块解析方式和 Patch 格式必须与当前 DSH 版本相符。

验证时建议先确认三件事：

  1. DSH 能否正常启动；
  2. 是否出现插件的加载日志；
  3. 插件报错时，能否从启动日志定位问题。

第三步：只增加一个真实功能

验证加载成功之后，再选择一个清晰的小目标，例如增加一个工具，或监听一个已有事件。一次只增加一种能力，方便判断问题出在模块加载、依赖声明、接口使用还是业务逻辑。

第四步：明确依赖和清理逻辑

如果插件需要使用其他服务，应按 Cordis 的方式声明依赖，而不是假设该服务一定存在。

如果插件注册了事件监听、定时器或其他持续性资源，还要考虑插件卸载时如何清理。插件的注册和副作用应尽量具备可撤销性，避免重复加载后出现重复监听、重复任务或资源泄漏。

第五步：稳定后再打包

当本地插件已经能够稳定运行，再补充 Bundle 的目录结构和清单。一个典型 Bundle 会包含：

my-dsh-plugin/
├── package.json          # 声明这是一个 DSH Bundle
├── cordis.patch.yml      # 声明要插入或覆盖的插件配置
└── index.js              # 插件入口模块

package.json 中的 dsh.bundle.patch 指向 Patch 文件。Bundle 不是插件运行逻辑的替代品，而是插件代码和配置的分发载体。

五、常见理解误区

  1. 把 Plugin、Bundle、Profile 当成同义词。 插件提供能力，Bundle 打包和分发插件配置，Profile 组合出一套运行环境。
  2. 以为所有功能都能直接通过 ctx 调用。 ctx 中的服务取决于当前运行环境；需要检查服务定义和依赖声明。
  3. 以为 Patch 会自动合并所有配置。 覆盖条目时可能替换整个 config，要核对原有字段。
  4. 一开始就把插件做成可发布包。 学习阶段先用本地 Patch 验证逻辑，稳定后再打包更容易定位问题。
  5. 没有确认扩展点就监听事件。 不同事件可能有不同的调用顺序和返回值约定；尤其是流程型事件，必须遵守对应的控制流程。
  6. 把插件加载成功等同于功能开发完成。 加载日志只证明入口模块被加载，不能证明工具、服务或事件逻辑已经按预期工作。

六、官方资料与建议阅读顺序

  1. DSH 中文架构说明：理解 Cordis、Profile、Bundle 和 Patch 的整体关系。
  2. Cordis 教程：学习插件、上下文、依赖和事件机制。
  3. DSH 基础开发文档：了解如何在 DSH 中加载和配置插件。
  4. 插件打包与安装：插件逻辑验证完成后，再学习 Bundle 的打包与安装。

本节总结

理解 DSH 插件系统时，建议牢牢记住这条链路：

DSH 提供运行环境 → Profile 选择组合方案 → Bundle 分发插件和配置 → Patch 叠加配置 → Cordis 加载插件并通过服务、依赖和事件组织协作。

开发自定义插件时，则反过来思考：

明确需求 → 选择扩展点 → 写最小插件 → 本地 Patch 加载验证 → 增加实际能力 → 最后按需打包成 Bundle。
